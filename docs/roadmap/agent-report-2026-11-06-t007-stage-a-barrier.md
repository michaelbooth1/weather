  means a dependency or settlement freshness check failed; the task supplies no
  blocker component/detail. Code alone cannot distinguish missing WU/labels/replay
  from economics, scoring infrastructure or date mismatch. Do not relax it.
  An actual implementation error in a returned blocker would be class (a), but
  no such root defect is established from the supplied facts.
- **Old target: unresolved host-state question.** A normal new Stage-A run pins
  Toronto yesterday once at start. The registrar does not pin October 7. An
  October-7 receipt in November therefore requires checking its run timestamp,
  actual scheduled action, explicit `--as-of` / `--settled-analysis-target-date`,
  and whether the latest run ever reached the barrier. It is not proof that the
  current daily invocation still targets October 7. Pre-barrier resource stops
  can leave an older standalone barrier JSON while the main status is current.
- **daily_learning stale: class (b).** It is a Stage-B producer, also produced by
  nightly training; both are held. Stage A does not execute it. Clearing Stage A
  does not refresh it. Its own adapter additionally requires a current,
  target-bound settlement `learning_status` PASS, then applies coverage,
  freshness and consistency gates and policy
  blockers. Fresh output is not synonymous with an OK learning verdict.
- **Scoreboard stale: class (b).** Also Stage B. Its input files are the weather
  proof packet, proper-scoring scorecard, residual-edge report, winner-rank
  parity, trading evidence, and optional daily-progress context. A green
  headline needs required schema-bearing inputs, anti-anchoring PASS and at
  least one countable weather-only, residual-edge or executable-profitability
  success lane. Running it does not create edge or valid trading evidence.
- **Aggregate rc 2 despite a repaired barrier: class (b) dependency scope.**
  The final `daily_rollup_freshness` check also compares `daily_learning.json`
  with newer granular outputs, including hourly/ten-minute and Stage-B reports.
  A stale/missing compact rollup can independently set pipeline `critical`.
  The sweep's KNOWN disposition does not change this Python gate or promotion.
  A zero daily exit while Stage B stays held is therefore a separate scope
  decision, not something a barrier repair alone promises.
- **False silence in monitoring: class (a), patched.** Stage A deliberately
  publishes COMPLETED for a terminal critical run. The existing sweep completion
  check accepts it without reading `payload_status` or `barrier`. The added
  `chain/stage_a_verdict` check independently requires completed/ok plus an
  ok/PASS target-matching barrier. Missing/negative verdicts remain CRITICAL;
  RUNNING is WARN alongside the independent abandoned/stale-run check.

**Where 2 originates:** adapters generally return dictionaries, not process
exit codes. A barrier BLOCK raises `SettledDayAnalysisBarrierError`; `run_step`
preserves its payload as typed error, the promotion lane contains it and skips
target-day promotion consumers, and the parent becomes `critical`. The CLI maps
critical/deferred/interrupted to 2, error/unreadable to 1, lock refusal to 3;
argparse also uses 2 for bad arguments, distinguishable by absence of a new run.
The wrapper forwards the child result, with its own deadline/lease refusals
75/76. Isolated step children return 0 for returned verdicts, 1 for exceptions,
130 for interruption. The quarantine standalone CLI has an optional rc-2 flag
which this adapter does not pass. Physical-family CLI returns normally even for
a negative report; neither is a normal direct source of the scheduled rc 2.
Other parent critical causes include current promotion receipt failures,
configured fleet/hourly/ten-minute/live-scorecard gates, scoring liveness,
economics BLOCK, readiness (Full mode), and final rollup freshness.

## Green conditions and safe treatment of parked alarms

Barrier PASS requires freshness PASS/WARN, no critical missing/error/negative
dependency or mismatched declared target, WU restoration before finalization,
and promotion-countable labels. Freshness checks snapshot folder/tape, labels
CSV, settlement ledger and sidecar, replay status/inputs and source status.
Countability uses material coverage where available. Diagnostic-only labels
do not become promotable. Hourly/ten-minute/trading BLOCK policy verdicts do
not themselves stop settled analysis; economics and infrastructure failures do.
`learning_status` excludes non-settlement readiness failures; it is not the
aggregate promotion verdict. This split already exists on the base.

Retain the canonical sweep `$knownCriticals` mechanism, already on the base
under DL R18: named producers must be exactly Disabled, a dated row must be
unexpired, at most 60 days, and renewal needs its own dated decision. KNOWN is
retained in JSONL and Markdown; missing/enabled producers, malformed rows and
expiry restore CRITICAL plus lapsed/malformed diagnostics. Do not change age
limits, forge refreshed outputs, disable the sweep, or run Stage B before B's
release to clear an alarm. The new Stage-A verdict check is outside those holds.

If master wants a green *settlement-only operational* exit while Stage B is
parked, propose an explicit stage/producer-scoped status contract separating
settlement execution from held learning and promotion readiness, with expiry
and re-arm tests. Preserve the full promotion verdict and stale artifact
evidence. This report does not authorize or implement that policy change.
T1's charter/simulator evidence is not certified by this legacy scoreboard.
