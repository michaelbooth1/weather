## 1. What production captures today (code trace)

US markets declare `metar, open_meteo, nws_hourly, nws_grid, mrms_precip, global_ensemble, open_meteo_multimodel` (`market/market_registry.py:130-265`). The fetcher adds `open_meteo_global_models` and `nbm_probabilistic_tmax` automatically (`model/model_sources.py:191-230`). WU (`wu_history`, `wu_current`) is disabled: `PAID_WEATHER_PROVIDER_ACCESS_ENABLED=False`, `model_constants.py:19`.

**Cadence.** One capture pass per market about every 9 minutes. The median gap between snapshots is 9.1-9.2 min in every block, p10 is 2.5-4 min, and there are 168-186 snapshots per market-day.

**Reuse rules:**
- Only the Open-Meteo family reuses a cached fetch, inside its TTL (`source_fetcher_with_budget`, `model_sources.py:435`; TTL `model_constants.py:35-55`; 120 min for multimodel and global models, 90 min for `open_meteo`).
- NBP is fetched once per cycle per pass scope through the fan-out.
- Every other source is fetched on every pass. The per-source TTL only bounds the last-good stale fallback.

**Storage.** Raw payloads are retained per snapshot (`collection/snapshot_store.py:1640-1720`, content-addressed; market-invariant payloads are shared).

## 3. Remaining-rise family: train/serve parity

1. **The anchor is already captured.** `guidance_physical_floor` takes the maximum of all METAR rows for the target local date. Those rows come from local midnight, because `metar_query_hours` asks for elapsed hours + 2, and `parse_metar_payload` converts reportTime to local before filtering by date. So the morning "midnight carry-over" concern in T3 Â§Serveability applies to `high_so_far` but not to the floor.
2. **Current temperature is captured, contrary to T2 Â§Serveability.** `current_temp` is a persisted feature (`feature_store.py:267,429`), METAR raw rows are retained per snapshot, and the reading is already passed to the lock-in as `metar_temp` (`model_distribution.py:518-534`). It is missing only from the 111h *extract*. A served version reads it directly, so no capture change is needed.
3. **Point-in-time parity with the hunters' history tables.**
   - **Freshness.** Production uses the newest report the API returns at fetch, about 3.8 min after the valid time (T17). The hunters required valid + 10 min. At serve time a stage would see a fall slightly earlier, which works in the stage's favour. A pre-registration should state the serve rule as "latest report in the captured payload".
   - **COR reports.** The hunters excluded COR. Production does not filter COR, and IEM keeps one row per valid time (T3 caveat). The difference is small, but it is a stated parity item.
   - **Units.** Production converts aviationweather Â°C (from the T-group) to Â°F without rounding. IEM `tmpf` comes from the same T-group. T16 showed the ASOS T-groups are whole Â°F except at KBKF, so a table built from IEM matches the served reading only if both use the same conversion. Declare the conversion and treat KBKF as the known edge.
   - **Fallback.** When the METAR fetch fails, the last-good payload is used and flagged `stale` (`official_current_stale` reaches the lock-in). The stage should fall back to served on stale, as the hunters fell back when no row was available.
4. **The model is untouched.** All forms are post-processing on the final distribution. HGBC features and the release are unchanged. Form A restores behaviour the release was built with while WU was live, so it moves serving *toward* the trained/validated state. Forms B and C add a new frozen artifact, which needs release binding (artifact hash, fit window up to 07-31, monthly refresh policy declared in advance).
5. **Data the forms need that the 111h extract lacks:** `current_temp` and the METAR rows. A faithful confirmation replays `estimate_distribution` on captured inputs (D-DEFECT Â§6), not the extract.

## 4. HRRR run matching (inconclusive)

`tools/research/model_parity/t20_capture_map.py` matched each captured `hrrr_high` to the full-local-day max of the Single-Runs 48-h HRRR runs (06/12/18Z; KSFO excluded for the grid-point mismatch documented by a-hrrr-aws). 7,738 snapshots had a unique match (within 0.15 F, runner-up more than 0.5 F away).

- Matched run age at fetch: p5 +0.1 h, p50 10.8 h, p90 26 h.
- 4.1% matched a run initialised *after* the fetch.

So the stitched Open-Meteo timeline, where past hours come from older runs and hourly runs are not in the Single-Runs set, makes day-max matching ambiguous, and it cannot date the run. The latency above therefore rests on the stated basis: Open-Meteo publication plus the measured fetch age. Facts are in `C:\swarm\out\t20\t20_capture_facts.json`.
