## Task 1: #209 Windows lane
- **Failure cause: a real, recurring test-timing flake, not a product bug.**
  - Every red master run since 10-12 failed **only** in `native-launch (status-rest)`, on one test: `tests/operations/test_replay_cache_compression_wrapper.py::test_abrupt_wrapper_exit_kills_entire_owned_tree`, with "fixture did not launch owned descendants".
  - The wrapper receipt reads "child deadline or monitored process memory ceiling reached", exactly 4 s after it started (14:18:55.45 to 14:18:59.52).
  - Affected runs: 38207667225 (10-12 05:22), 38355799288 (06:16), 38355946127 (06:18) and 38410615599 (14:07). Each shows 1 failed / 200 passed.
  - Runs 38351441191 and 38367397542 were green. The two 06:17-06:18 runs marked "cancelled" were superseded by concurrency, not failures.
  - Mechanism: the test launches `hang` mode, which injects the fixture's 4 s wrapper deadline. On a slow runner the wrapper hard-stops before the child has spawned its grandchild and written `descendant.json`.
  - f218b40fa (10-04) already made the success modes use a 30 s ceiling but missed this test. The test kills the launcher itself, so it only needs a ceiling. Its assertion `not wrapper-result.json` is also racy under a 4 s hard stop.
  - It is not the launch-shard stall, not shard drift and not a mutex race.
- **Fix:** branch `claude/windows-lane-fix-20261014`, head **`cd8553f0c`**, draft **PR #284**. The change is test-only (roll-free):
  - `launch()` takes a `deadline_seconds` parameter, and the abrupt-exit test passes 30.
  - The parametrized `hang` case keeps 4 s, which still proves the hard stop.
  - No assertion changes.
- **Tests:** `qtest wlf`, **123 passed**. Files: the fixed file (it runs natively here), `test_windows_qualification_shards.py` and the 9 ratchets.
